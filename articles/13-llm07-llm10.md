# Article 13: LLM07–LLM10: Misinformation, Hidden Context, Vector Weaknesses & Output Handling

The last four LLM risks show how many different security boundaries exist around an AI application.

## LLM07 — Misinformation

A model can produce an answer that sounds authoritative but is unsupported or incorrect.

Security controls may include:

- Grounding
- Source validation
- Citation checks
- Confidence/calibration monitoring
- Human review for high-impact outputs

## LLM08 — Hidden Context Exposure

AI applications may contain:

- System instructions
- Hidden context
- Memory
- Internal metadata
- Tool descriptions

The security question is:

> What context should the model see — and what context should the user ever be able to recover?

Context should therefore be treated as sensitive application state.

## LLM09 — Vector and Embedding Weaknesses

RAG systems introduce another layer:

**documents → chunks → embeddings → vector store → retrieval → context**

Security failures can occur through:

- Unauthorized retrieval
- Tenant leakage
- Index manipulation
- Retrieval poisoning
- Weak metadata filtering

> **The vector database is a security boundary.**

## LLM10 — Improper Output Handling

If downstream software treats model output as trusted input, the model can become an injection path into another system.

For example:

**LLM output → SQL**

**LLM output → HTML**

**LLM output → code**

**LLM output → shell command**

**LLM output → API parameter**

The rule is simple:

> **LLM output is untrusted input. Validate it before execution.**

Across these four risks, the same architecture principle appears repeatedly:

> **Do not give the model implicit trust.**

Treat model input, context and output as untrusted data unless independently validated.
